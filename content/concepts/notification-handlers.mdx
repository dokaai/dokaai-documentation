A notification handler defines the configuration used when a notification is triggered. Its settings connect channel configuration, channel templates, recipient selection and customer preference associations.

## Configuration and execution

| Object or action | What it represents |
| --- | --- |
| Handler | Named notification configuration within a project |
| Channel configuration | Enabled channel and provider integration choices |
| Channel template | Content, variables and publication state for a channel |
| Recipient source | Payload-based contacts, a target list or a cohort |
| Trigger | A request to run the handler with the supplied data |
| Handler event | An execution record you inspect after triggering |

Handler publishing state and template publishing state are separate settings. Editing a template is not the same action as publishing it, and submitting a trigger is not evidence that a recipient received a message.

## Build and inspect

[Configure the handler](/build/handlers), then its [channels](/build/channels), [recipients](/build/recipients) and [templates](/build/templates). Use [test/send](/build/test-and-send) to exercise the configuration and [notification events](/operations/events) to inspect the result.

Project background jobs, such as customer imports and cohort queries, have a separate inspection surface. Their status should not be read as notification delivery status.

## Notification events

A notification event records an individual handler trigger and its execution information. The handler defines reusable configuration; the event lets you investigate one run with its particular mode, recipients and data.

For example, an order-confirmation handler can be triggered for two different orders. You inspect the event for the relevant trigger when investigating one customer's result, rather than assuming the handler's current settings explain every past run.

### The objects involved

| Object | Purpose |
| --- | --- |
| Handler | Configuration for a notification |
| Trigger request | Input asking the handler to run |
| Event ID | Identifies the event record |
| Idempotency key | Correlation/deduplication-related value shown with an event; exact replay semantics depend on the API contract |
| Snapshot | Handler configuration captured in the event data, when present |
| Overrides | Inputs supplied for that run, when present |
| Execution | Reported progress and results of the processing stages |

The events interface is labelled **Observability - Beta**. Available detail depends on the data returned for the event. A missing field is not automatically evidence that a stage failed.

### Execution stages

The detail view organizes available execution information into **Trigger**, **Routing**, **Template** and **Delivery**. These help locate where recipients were resolved, values mapped or payloads dropped, and channel results recorded.

An event is not a background import/query job, and a reported channel count is not proof that a customer opened a message. Use [Inspect notification events](/operations/events) for the fields, tabs and investigation steps. Use [Background jobs](/operations/jobs) for CSV import and audience-query work.
