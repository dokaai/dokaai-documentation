Customer-scoped APIs act on behalf of one customer, such as an in-app inbox or preference screen. They use customer bearer authentication, separate from the client credentials your backend uses to trigger a handler.

## Signing keys

Customer signing keys support customer-scoped authentication. They are separate from the client credentials used for server-to-server API requests. This guide covers the dashboard key-management task; the existing [Authentication reference](/api-reference/authentication) owns the customer-token contract.

### Create a key

1. Open **Customer Auth Keys** in the selected organization.
2. Choose the intended product space in the available controls.
3. Create a customer auth key and review the returned signing-key information.
4. Copy or download the private file when it is shown. Store it securely on the backend that will sign tokens; the success dialog warns that it will not be shown again.

Keep the private file out of customer devices, source control and support logs.

### Review key changes

The dashboard offers **Rotate**, **Deactivate** and **History** actions. Review the selected product space and signing-key ID before confirming a key change. Coordinate changes with the application owner and review the resulting active-key/history state.

Confirm the accepted production token and key-transition behavior for your deployment before changing a live integration. Key-management controls alone do not establish token overlap or expiry guarantees.

For access or token issues, start with [Authentication diagnostics](/troubleshooting/authentication). For ordinary backend triggering, use [API credentials](/account/api-credentials) instead.

## Prepare the identity context

You need the relevant product space, its [customer signing configuration](/developers/customer-authentication#signing-keys), and the customer identifier used by your application. The signing result includes identifiers such as the product-space code, workspace ID and signing-key ID. Use those values; do not substitute a project ID for a workspace ID based on its name.

The existing [Authentication reference](/api-reference/authentication) owns the JWT algorithm, required claims, header format and token examples.

## Implement the application flow

1. Authenticate the customer in your own application.
2. On your backend, resolve the customer's identity and the intended product-space signing configuration.
3. Generate a short-lived customer token using the existing authentication contract. Keep the private signing key on the backend.
4. Give the client the resulting token, not the signing key or client secret.
5. Use the customer token for [in-app APIs](/developers/in-app) or [preference APIs](/developers/customer-preferences), then handle expiry and rejected-token responses.

Do not expose a production signing endpoint that lets an unauthenticated caller choose another customer's identity. Derive or authorize the identity from the application's authenticated session.

## Verify integration

Check the accepted identity/claim contract against your deployment, test with a controlled customer and inspect authorization failures before releasing. The local demo illustrates token generation and API calls; it is not proof of a supported distributable SDK or production token acceptance.

See [Authentication diagnostics](/troubleshooting/authentication) for token, product-space and key-state issues.
