Use the developer path when an application needs to trigger a configured notification handler. Dashboard configuration and API integration can be owned by different teammates.

## Trigger from your backend

1. Obtain the organization/project context and the configured handler's identifiers from the dashboard team.
2. [Create and store client API credentials](/account/api-credentials).
3. Read the existing [Authentication reference](/api-reference/authentication).
4. Follow [Trigger notifications from an application](/developers/trigger-notifications) and inspect the resulting [handler event](/operations/events).

If the handler is not configured yet, use [Quickstart](/quickstart) or the [handler configuration guide](/build/handlers). A dashboard test is useful validation, but you do not need to repeat it merely to read the API integration path.

## Use canonical contracts

The [API Reference](/api-reference) owns exact request fields, headers and responses. The existing [Integration directory](/integration) owns provider discovery and setup. This section connects those contracts to the product tasks without duplicating them.

## Customer-scoped APIs

Customer bearer authentication is a separate path from client credentials. Start with [Customer authentication](/developers/customer-authentication) and the [signing-key guide](/developers/customer-authentication#signing-keys), then choose [In-app notifications](/developers/in-app) for an inbox or [Customer preferences integration](/developers/customer-preferences) for a preference screen. Those guides explain the application flow and link to the existing canonical contracts. Confirm the accepted identity/deployment contract before release.
