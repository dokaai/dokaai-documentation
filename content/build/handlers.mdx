A [notification handler](/concepts/notification-handlers) is reusable configuration for a notification, such as an order confirmation. Create it in the intended [project](/account/setup), after its service is enabled and a [customer pool](/customers/pools) is available.

## Fill in the basic details

Open the project's **Notification Handler** area and create a handler. Review each field before saving:

| Field | What to decide |
| --- | --- |
| Name | A recognizable dashboard name, such as Order confirmation |
| Notification Handler Key | A unique key for the handler; it can be edited during creation and cannot be changed afterward |
| Customer Pool | The pool associated with the handler; this selection is also fixed in the existing-handler edit form |
| Notification type | Transactional, Marketing or Services, according to the message's purpose |
| Priority | One of the values available for the selected notification type |
| Notification subtype | An optional subtype within that type, where needed |
| Message frequency | Real time or Scheduling |

The name and key are different fields. Keep the handler ID/key required by the API handoff rather than assuming the display name is sufficient.

## Type, priority and subtype

An order receipt is an example of a transactional message, a promotional announcement is a marketing example, and an operational service update is a service-message example. Choose the classification appropriate to your actual use and organization settings.

The current form offers P1–P5 for Transactional, P2–P5 for Services and P3–P5 for Marketing. These are handler priority choices, not a delivery-time guarantee. A subtype provides a more specific named classification and can be relevant to the configured DND bypass selection. See [Send policy](/preferences/send-policy).

## Choose the triggering path

**Real time** configures the handler's real-time path; **Scheduling** adds schedule configuration to the setup flow. Review changes to this choice carefully: the form can ask you to change a payload-based recipient source or confirm a schedule-impacting change. See [Configure recipients](/build/recipients) and [Schedule notifications](/build/schedules).

## Complete and test the configuration

Save the basic details, then configure [channels](/build/channels), [recipients](/build/recipients), [templates](/build/templates) and [preferences](/preferences/groups-and-topics#handler-preferences). Handler publishing state and each template's publication state are separate. Saving the basic details does not send a notification.

Run a controlled [test send](/build/test-and-send) and inspect its [event](/operations/events). The existing [Get Notification Handler operation](/api-reference/notification-handlers/get-notification-handler) owns the API contract.
